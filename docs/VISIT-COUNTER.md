# 累计访客数（UV）

用户要求避免重复刷新让底部数字逐次累加，已将原累计访问量（PV）改为累计独立访客数（UV）。接入[不蒜子原版计数服务](https://busuanzi.ibruce.info/)，无需注册、密钥或项目后端；[服务文档](https://ibruce.info/2015/04/04/busuanzi/)说明PV按浏览次数累计，UV按访客去重。

## 统计口径

正式HTTPS网站每次打开或刷新发起一次请求，显示服务响应中的`site_uv`，不再读取`site_pv`。即使响应中的PV增加，只要UV没有变化，页面访客数就保持不变；缺少UV时显示“暂不可用”，不拿PV凑数。

模块缓存同一页面加载的请求与结果，React StrictMode重播、组件重挂载、切换城市、车站、列车类型或搜索不重复发送。刷新后由服务方按UV规则识别访客，不是前端用本地缓存冒充全站去重。

UV不等于严格的设备数量。原服务文档没有明确公布设备识别方法及去重周期，不能承诺同设备永久只记一次或每天只记一次；换浏览器、无痕访问、浏览器限制及服务识别规则均可能影响结果。本轮实现用户批准的UV方案，没有新增自定义每日去重或设备指纹。

仅正式HTTPS域名启用；localhost、本地IP、IPv6、`.local`、`.localhost`、`.test`、`.invalid`及HTTP预览不联系服务，显示“上线后开始统计”。等待时显示“加载中…”，网络错误、超时或无效结果显示“暂不可用”，不会编造数字。没有自动重试，以免失败请求重复发送。

同一个GitHub Pages域名下的不同仓库可能共享统计，不是沿线独占数据库。独占总数需使用只承载沿线的自定义域名或接入独立站点标识的服务。更换域名对应另一份统计，过去未接入服务的访问不能补回。旧PV不会直接换算成UV，现在读取服务维护的UV总数。

广告拦截、禁止JavaScript、网络故障等可能漏计。第三方服务的口径、历史数据及可用性由服务方维护。

## 请求与显示

`src/lib/visitCounter.ts`使用原版嵌入脚本的JSONP协议：`https://busuanzi.ibruce.info/busuanzi?jsonpCallback=BusuanziCallback_...`。读取`site_uv`，验证整数后格式化显示，不将返回内容作为HTML插入。

动态脚本使用`referrerPolicy=origin`，只发送站点协议与域名，不发送本站URL中的车站、城市和搜索参数；请求URL只有随机回调标识。没有额外埋点、设备标识存储或本地累计。服务方仍接收正常网络请求的IP和浏览器信息；JSONP响应作为脚本执行，与原服务嵌入方式相同。

`src/components/VisitCounter.tsx`在全站页脚显示“累计访客数 … 人次”，首页与所有城市共用。数据说明弹窗同步解释UV与去重边界。

## 验证与部署

7项测试覆盖本地不发送、同页并发只请求一次、URL筛选不发送、超时/错误/迟到响应、无效值和大整数。测试特别覆盖PV增加而UV不变时保持相同访客数，以及拒绝只有PV的响应。严格TypeScript与生产构建通过；本地浏览器核对页脚与手机布局。

部署与现有GitHub Pages流程一致，无须配置。真实数值须在正式HTTPS域名部署后由服务响应；本轮没有线上发布，也未向他人的域名发送测试计数请求。上线后检查底部显示访客数，重复刷新是否保持应按服务方实际UV结果观察，不能以本地测试宣称已验证服务方设备识别。
